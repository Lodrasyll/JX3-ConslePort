## 0. 项目管理原则

本文件用于把技术方案拆成可执行、可验收、可暂停和可回滚的开发任务。

每个阶段都必须有：目标、前置条件、任务、交付物、验收标准、风险和停止条件。

**代码写出来不等于任务完成。**
只有在目标客户端中通过可复现测试、符合当前规则，并有记录证据，任务才算完成。

### 0.1 状态定义

  状态     含义
  -------- -------------------------------------
  未开始   尚未开展
  进行中   正在执行，尚无完整验收证据
  待验证   有源码/设计线索，等待当前客户端验证
  阻塞     被规则、权限、接口或环境问题阻断
  已通过   验收标准全部满足，证据已归档
  不采用   经评估决定不走该路线

### 0.2 优先级定义

-   **P0**：决定项目能否继续的阻断项。
-   **P1**：MVP 必需能力。
-   **P2**：体验完善和兼容性工作。
-   **P3**：长期增强功能。

### 0.3 每项任务的证据要求

记录测试日期、客户端版本、插件版本/提交号、测试设备与映射配置、操作步骤、预期与实际结果、截图/日志/录屏（如规则允许）、结论和遗留问题。

## 1. 项目目标与 MVP 定义

### 1.1 P0 / MVP 必须实现

1.  目标客户端为 Windows PC《剑网3》旗舰版。
2.  具备合法、可复现的自制插件测试途径。
3.  最小 Lua 插件能按当前规则加载。
4.  手柄可通过获准方式完成基础移动、镜头和跳跃。
5.  RT、LT 两个修饰层稳定映射 16 个手动技能位。
6.  Lua HUD 展示 16 个技能槽位及对应按键说明。
7.  若 API 允许，显示真实技能图标和冷却；否则降级为静态图标/文字。
8.  键鼠操作不被破坏，插件可以关闭或隐藏。

### 1.2 MVP 不包含

完整环形菜单、所有门派自动技能识别、自动目标选择、自动连招/自动输出、原生摇杆
API 自研替代、客户端注入、内存操作或安全机制绕过。

### 1.3 完成定义（Definition of Done）

MVP 只有在以下全部成立时才算完成：

-   当前旗舰版插件加载流程通过。
-   所用接口均有许可与版本验证记录。
-   手柄输入稳定，无卡键、双重输入和失焦持续输入。
-   RT/LT 两层 16 个技能位可手动触发。
-   HUD 与实际绑定一致。
-   插件关闭后恢复原有键鼠体验。
-   无已知规则违规或第三方代码许可问题。
-   文档、配置和测试记录齐全。

  ID      任务                                 负责人      初始状态
  ------- ------------------------------------ ----------- ----------
  S1-01   确认当前 Interface 插件目录          用户        待验证
  S1-02   确认当前 `info.ini` 格式与入口字段   用户 + AI   待验证

  S1-08   建立 API 来源、许可、行为三级记录    AI          未开始

### API 探测顺序

1.  Lua 基础环境是否可运行。
2.  插件入口是否执行。
3.  当前允许的 UI 初始化接口。
4.  当前允许的事件注册接口。
5.  快捷键注册与读取能力。
6.  玩家身份/技能数据的只读能力。
7.  技能图标与冷却读取能力。
8.  UI 缩放与配置持久化能力。

### 候选 API 名称

此前从历史插件源码或资料发现的候选名称：

-   `Hotkey.AddBinding`
-   `Hotkey.Get`
-   `IsKeyDown`
-   `OnFrameKeyDown`
-   `RegisterEvent`
-   `UI_GetClientPlayerID`
-   `Table_GetSkillIconID`
-   `GetSkill`
-   `GetSkillCDProgress`
-   `Station.GetUIScale`
-   `LoadLUAData`
-   `SaveLUAData`

这些名称都必须记录来源。`Hotkey.AddBinding`、`Hotkey.Get`、`GetSkill`
等可能是茗伊内部封装，而非客户端全局 API。未验证前禁止直接依赖。

### 交付物

-   `addon/info.ini`
-   `addon/Main.lua`
-   `docs/API_VERIFICATION.md`
-   `docs/LOAD_TEST_REPORT.md`

-   插件在当前规则允许的环境中被识别。
-   入口执行成功。
-   没有绕过认证或安全限制。
-   API 表中每个候选项标记为通过、不通过或待确认。
-   未验证 API 不进入正式模块。

## 5. 阶段 S2：手柄输入原型

**优先级：P0**

### 目标

验证手柄到游戏原生键鼠输入的基本链路。

### 首选方案

在规则允许的前提下使用 Steam Input：

-   左摇杆 -\> WASD。
-   右摇杆 -\> 相对鼠标移动。
-   A/X/Y/B 与方向键 -\> 技能槽位。
-   RT -\> 第一技能层。
-   LT -\> 第二技能层。
-   暂不实现 LT+RT 第三层。

### 任务清单

  ID      任务                           负责人      初始状态
  ------- ------------------------------ ----------- ----------
  S2-01   建立 Xbox 布局基础配置         用户 + AI   未开始
  S2-02   测试左摇杆 WASD                用户        未开始
  S2-03   测试右摇杆镜头映射             用户        未开始
  S2-04   测试跳跃和基础按键             用户        未开始
  S2-05   建立 RT 技能层 1--8            用户 + AI   未开始
  S2-06   建立 LT 技能层 9--16           用户 + AI   未开始
  S2-07   测试修饰层覆盖与优先级         用户        未开始
  S2-08   测试聊天框、失焦、断连和重连   用户        未开始
  S2-09   整理门派键位冲突表             用户        未开始

### 输入验收

-   基础移动可控，斜向输入正常。
-   右摇杆稳定控制视角，灵敏度可调整。
-   RT 与 LT 层不会同时触发基础层动作。
-   每次物理按键只触发预期的一次游戏输入。
-   松开修饰键后没有 Ctrl/Shift 等状态残留。
-   聊天框聚焦时不会意外施放技能。
-   游戏失焦或手柄断开时不会持续移动或卡键。
-   键鼠仍可正常操作。

### 交付物

-   Steam Input 配置导出或配置记录。
-   `docs/INPUT_MAPPING.md`
-   `docs/INPUT_TEST_REPORT.md`

### 停止条件

若映射造成重复输入、失焦持续输入或无法解除的修饰键状态，停止使用该配置并修正，不进入
HUD 联调。

## 6. 阶段 S3：CrossHotbar HUD

**优先级：P1**

### 目标

制作 16 个技能位的十字技能栏，视觉提示与实际输入映射一致。

### 任务清单

  ID      任务                         负责人      初始状态
  ------- ---------------------------- ----------- ----------
  S3-01   确定 HUD 布局与屏幕位置      用户 + AI   未开始
  S3-02   建立 16 个槽位的数据结构     AI          未开始
  S3-03   建立技能图标占位显示         AI          未开始
  S3-04   显示 A/X/Y/B/D-pad 标签      AI          未开始
  S3-05   区分 RT 与 LT 两组技能       AI          未开始
  S3-06   增加 HUD 显示/隐藏           AI          未开始
  S3-07   增加缩放、透明度和位置配置   AI          未开始
  S3-08   测试常见分辨率和 UI 缩放     用户        未开始

### 数据结构建议

``` text
HotbarSlot
├── slot_id
├── layer            # RT / LT
├── button           # A / X / Y / B / D-pad
├── display_name
├── icon
├── game_key
└── cooldown_state   # 可选，API 验证通过后启用
```

### P0 HUD 原则

-   初始可由玩家手动配置技能名称和图标。
-   不因技能数据 API 尚未通过就阻断 HUD 原型。
-   不能可靠获知 RT/LT 状态时，同时显示两组技能，不做动态高亮。
-   不遮挡游戏关键 UI。
-   HUD 关闭后不影响原生键鼠和技能栏。

### 验收标准

-   16 个槽位全部正确显示。
-   按键标签与输入配置一致。
-   RT/LT 分组清楚。
-   HUD 位置、大小和透明度可调整。
-   不出现明显 UI 遮挡或高频刷新问题。

## 7. 阶段 S4：技能图标与冷却信息接入

**优先级：P1**

### 目标

在 API 验证通过后，将静态 HUD 升级为动态技能 HUD。

### 任务

1.  确认技能 ID 与图标 ID 的对应关系。
2.  确认图标资源是否可通过允许的接口读取。
3.  确认当前玩家技能槽位与技能数据之间的关系。
4.  确认冷却进度返回值单位、范围和更新时机。
5.  测试冷却开始、进行中、结束和技能不可用状态。
6.  限制刷新频率，避免每帧重复查询所有技能。
7.  为 API 不可用或返回空值提供静态显示降级方案。

### 验收标准

-   图标与技能对应正确。
-   冷却显示与游戏内状态一致。
-   无效技能 ID 不导致插件崩溃。
-   API 不可用时 HUD 仍可工作。
-   不读取未授权或非公开数据。

## 9. 阶段 S6：后续功能（不进入 P0）

### S6-A：RingMenu 环形菜单

-   8 方向菜单布局。
-   当前选项高亮。
-   确认、取消、返回。
-   菜单项对应地图、背包、任务、角色、社交、设置等入口。
-   每项操作必须由玩家主动触发。

### S6-B：Target HUD

-   只接入当前允许读取的目标信息。
-   不实现自动锁定、自动切换或自动选择目标。
-   目标信息缺失时隐藏对应字段。

### S6-C：轻功操作模式

单独研究地面移动到起跳的切换、二段跳/空中方向控制、镜头与移动同时操作、轻功技能手动快捷键安排、落地与方向修正。轻功操作必须由玩家手动输入，不开发自动飞行或自动寻路。

### S6-D：多门派 Profile

-   每个门派一份默认布局。
-   每个角色可覆盖门派默认值。
-   提供导入/导出配置。
-   配置不绑定账号凭证或敏感信息。

## 11. 变更控制

任何影响架构、输入映射或 API 依赖的变更，都要记录：

``` text
变更编号：
日期：
提出人：
变更原因：
原方案：
新方案：
影响模块：
是否影响官方规则：
是否需要重新测试：
批准结论：
```

以下变更必须重新走相关阶段验收：

-   更换客户端版本或分支。
-   更换输入工具或映射方式。
-   修改 RT/LT 层优先级。
-   新增游戏 API 依赖。
-   引入第三方插件框架。
-   增加自动化或批量输入行为。
-   变更插件加载或认证方式。

## 12. 每轮执行节奏

**每轮开始：**

-   选定 1--3 个可验收任务。
-   明确依赖和测试环境。
-   确认本轮不触碰未经许可的接口。

**开发中：**

-   AI：代码草案、模块拆解、静态检查、测试用例。
-   用户：客户端环境、真实操作、结果记录。
-   每次只引入少量新 API，便于定位问题。

**每轮结束：**

-   运行测试。
-   更新任务状态。
-   保存截图/日志/版本信息。
-   记录失败原因和降级决策。
-   决定继续、返工或停止。

不要一次性生成整套插件后再去游戏里排错。先完成入口，再完成单一
API，再完成单一 UI 模块。

## 17. 本阶段最终决策

**先做验证，再做完整产品。**

当前不应优先投入复杂 HUD、美术资源或多门派配置。项目最先要拿到三个答案：

1.  当前 PC 旗舰版是否允许按规则加载自制 Lua 插件？
2.  哪些快捷键、技能数据和 UI API 是当前允许使用的？
3.  Steam Input 的手柄到键鼠映射能否稳定、合规地控制游戏？

三个答案明确后，才能判断 JX3 ConsolePort 的 MVP
是完整可行、需要降级，还是被当前客户端规则/接口阻断。

本文件与《JX3 ConsolePort（PC
旗舰版）技术方案》共同构成当前项目基线。后续每次实测都应更新本文件的状态、证据和决策记录。
