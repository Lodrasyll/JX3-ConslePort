## 0. 本文目的

本文记录此前讨论中已经形成共识的产品方向和重要功能设计，重点回答：

-   我们究竟要做一个什么样的剑三手柄插件？
-   它和简单的手柄键位映射有什么区别？
-   玩家用手柄时，战斗、移动、视角和界面应该如何组织？
-   哪些功能属于第一版核心，哪些应该后置？
-   当前方案有哪些已经确定的决策，哪些仍然需要验证？

本文是产品与交互设计基线，不是 API
可用性证明。具体实现仍以技术方案和实施控制文档为准。

## 1. 产品定位与愿景

### 1.1 一句话定义

**JX3 ConsolePort 是一套面向《剑网3》PC
旗舰版的手柄优先交互插件：以手柄作为主要操作设备，通过组合键技能层、手柄友好
HUD、快捷菜单和逐步完善的界面导航，让传统 PC MMO
的键鼠操作尽可能转化为舒适、连续、可配置的手柄体验。**

### 1.2 不只是"手柄映射器"

简单映射器只解决：

> 按下手柄某个按钮，相当于按下键盘某个键。

JX3 ConsolePort 希望进一步解决：

-   玩家如何知道当前按钮对应什么技能？
-   16 个以上技能如何在有限按钮上组织？
-   如何在战斗中切换技能组而不打断操作？
-   如何用手柄完成常见界面入口和菜单选择？
-   如何让移动、视角、战斗与轻功之间的操作自然衔接？
-   如何让不同门派、角色和玩家习惯拥有独立配置？

因此，项目由两部分构成：

1.  **输入适配**：把手柄操作转化为游戏允许接收的输入。
2.  **交互体验层**：用 Lua 插件提供
    HUD、技能栏、菜单和设置，让玩家理解并管理手柄操作。

### 1.3 参考对象与借鉴重点

  WoW ConsolePort         手柄优先理念、修饰键、虚拟鼠标、HUD、配置体系   WoW 专用 API 和代码

## 2. 已形成的核心设计决策

以下是目前讨论中已确定的方向。技术实现仍需经过当前旗舰版验证。

### 决策 1：以 PC 旗舰版为唯一首要目标

-   第一阶段不同时兼顾极速端、移动端或掌机端。
-   所有插件加载、API 和 UI 方案先以 PC 旗舰版为准。
-   其他客户端以后作为独立兼容工作，不反向拖累 P0。

### 决策 2：采用"输入层 + Lua 交互层"的双层架构

-   输入层优先研究官方原生输入能力；如不存在可用接口，再评估规则允许的
    Steam Input 键鼠映射。
-   Lua 层负责 HUD、技能槽位、按键提示、菜单和配置。
-   不假定 Lua 能直接读取 XInput、摇杆轴或扳机状态。
-   如果 Lua 无法获知 RT/LT
    当前状态，第一版可以静态同时显示两组技能，不强求动态高亮。

### 决策 3：优先采用 Cross Hotbar 思路

-   RT 与 LT 作为两个主要技能修饰层。
-   每层 8 个槽位。
-   第一版提供 16 个可手动触发的技能位。
-   暂不加入 LT+RT 第三层，避免输入优先级和冲突复杂化。
-   组合键的实际映射必须由当前可用且合规的输入方案实现。

### 决策 4：输入必须保持玩家主动控制

-   每次技能输入对应玩家明确的手柄按键操作。
-   不做自动输出循环、自动连招、自动施法、自动选招或自动目标选择。
-   不通过客户端注入、内存读写、驱动伪装或安全机制绕过实现功能。

### 决策 5：先做最小闭环，再扩展完整体验

第一版优先验证：

1.  插件可按规则加载。
2.  手柄可完成基础移动、视角和跳跃。
3.  RT/LT 两层技能映射可靠。
4.  Lua HUD 显示对应技能槽位。
5.  插件不破坏原有键鼠体验。

环形菜单、目标 HUD、轻功专用模式、多门派配置等放在 MVP 之后。

## 3. 目标用户体验与操作原则

### 3.1 核心体验目标

玩家应当能够：

-   坐在正常游戏距离之外，以手柄完成主要游戏操作。
-   不需要记忆大量键盘组合，能通过 HUD 知道技能位置。
-   左手负责移动、镜头以外的辅助输入和修饰键；右手负责主要技能与确认操作。
-   在战斗中尽可能少离开摇杆和主要按键。
-   在探索、轻功、菜单和战斗之间切换时，不需要频繁拿起键盘鼠标。

### 3.2 交互设计原则

**原则 A：手柄操作必须可见**

HUD
必须告诉玩家当前有哪些技能槽、对应什么按键、属于哪一个技能层。不能只提供一套隐形映射。

**原则 B：常用操作优先，低频功能后置**

战斗、移动、跳跃、目标相关操作优先于聊天、背包整理等低频操作。

**原则 C：避免输入冲突**

同一个物理按键在不同层可以承担不同功能，但必须保证修饰层优先级清晰，不得一次操作触发两个意外行为。

**原则 D：允许键鼠混合使用**

第一版不追求彻底移除键鼠。聊天、复杂设置、物品整理等功能允许玩家临时使用鼠标键盘。

**原则 E：可配置而不是强制一种布局**

门派技能数量、玩家习惯和键位冲突不同。后续应允许玩家调整槽位和绑定，不把一套固定方案写死。

**原则 F：先保证可靠性，再追求操作密度**

不以堆叠更多组合键作为目标。宁可先稳定支持 16
个技能位，也不急于设计三层、四层复杂组合。

## 4. 核心输入布局：双扳机 Cross Hotbar

### 4.1 主要布局

首版以 Xbox 布局作为设计基准，PlayStation
手柄以后通过输入映射适配成同样的逻辑按钮名称。

  物理输入   基础层候选功能   RT 技能层   LT 技能层
  ---------- ---------------- ----------- -----------
  A          跳跃/确认        技能 1      技能 9
  X          交互/确认候选    技能 2      技能 10
  Y          菜单/功能候选    技能 3      技能 11
  B          取消/返回        技能 4      技能 12
  十字键 ↑   常用操作候选     技能 5      技能 13
  十字键 ←   常用操作候选     技能 6      技能 14
  十字键 →   常用操作候选     技能 7      技能 15
  十字键 ↓   常用操作候选     技能 8      技能 16

说明：

-   基础层功能只是候选，最终必须根据剑三原生键位、游戏焦点行为和玩家习惯确定。
-   RT 和 LT 是修饰层，不代表 Lua 一定能实时读取其状态。
-   当 RT 按住时，RT 层必须覆盖对应基础层按键，不能同时触发基础层动作。
-   LT 同理。
-   P0 不定义 LT+RT 第三层。

### 4.2 候选键盘映射

  手柄逻辑按钮   RT 层输出   LT 层输出
  -------------- ----------- -----------
  A              `1`         `Ctrl+1`
  X              `2`         `Ctrl+2`
  Y              `3`         `Ctrl+3`
  B              `4`         `Ctrl+4`
  D-pad ↑        `5`         `Ctrl+5`
  D-pad ←        `6`         `Ctrl+6`
  D-pad →        `7`         `Ctrl+7`
  D-pad ↓        `8`         `Ctrl+8`

这是映射设计草案，不是已验证的游戏内键位配置。正式使用前要检查原生快捷键冲突、修饰键支持、输入工具行为与规则许可。

### 4.3 为什么先做两层而不是更多层

-   16 个槽位足以验证核心操作模型。
-   两个扳机在手柄上容易理解，符合常见 Cross Hotbar 设计。
-   第三层会增加组合状态、优先级和 HUD 状态同步的复杂度。
-   当前尚未确认 Lua
    能否获知扳机状态，因此不宜先设计高度依赖动态层状态的 UI。

### 4.4 技能槽位的视觉表达

每个槽位建议包含：

-   技能图标。
-   技能名称或缩写。
-   对应手柄按钮标识。
-   RT/LT 层标识。
-   冷却遮罩（仅当技能冷却 API 验证通过）。
-   可选的可用状态提示（仅当有合法、可靠的数据来源）。

第一版可以先用手工填写的技能名称和图标占位，后续再接入真实技能数据。

## 5. 移动与视角操作方案

### 5.1 左摇杆：移动

P0 候选方式：

-   左摇杆前后左右映射为 WASD。
-   先确保基础移动、斜向移动和松杆停止稳定。
-   测试摇杆死区、斜向输入、对角线速度和短距离微调。
-   第一版不承诺真正的模拟量行走；只有在游戏原生支持或允许的映射能力得到验证后，才考虑模拟量控制。

### 5.2 右摇杆：视角

P0 候选方式：

-   右摇杆映射为相对鼠标移动。
-   测试水平与垂直灵敏度、反向、加速度、死区和镜头边界。
-   验证是否需要持续按住鼠标右键或其他鼠标键才能旋转视角。
-   右摇杆必须能与左摇杆同时工作。
-   如果镜头控制不稳定，先保留鼠标作为补充，不为了"全手柄"牺牲可玩性。

### 5.3 基础移动/镜头验收

-   前后左右移动方向正确。
-   斜向移动不出现明显异常。
-   移动中能够连续转动视角。
-   松开摇杆后不会持续移动或镜头漂移。
-   手柄断开或切换窗口后不会卡住输入。

## 6. 轻功：剑三特有的重点功能

轻功是剑三手柄方案与普通 MMO
手柄方案的重要区别，不能简单套用普通跑跳逻辑。

### 6.1 设计目标

让玩家能够通过手柄完成：

-   地面移动与起跳。
-   空中方向控制。
-   空中视角调整。
-   轻功技能的手动触发。
-   落地前后的方向修正。
-   轻功与普通战斗/移动操作之间的切换。

### 6.2 设计策略

轻功先作为独立的后续操作模式研究，不进入 P0 的硬性完成条件。

首轮测试只验证：

1.  左摇杆移动与右摇杆视角能否同时工作。
2.  跳跃/轻功相关原生快捷键能否稳定映射。
3.  空中操作时技能层是否仍可用。
4.  扳机和面键组合是否会妨碍方向控制。
5.  落地、转向和连续操作是否有明显输入冲突。

### 6.3 暂不实现

-   自动飞行。
-   自动寻路。
-   自动轻功连段。
-   自动判断地形并选择轻功技能。

所有动作由玩家手动输入。

## 7. CrossHotbar HUD：第一核心 UI

### 7.1 目标

HUD 是本项目区别于普通手柄映射器的核心功能之一。玩家应能直接看到 16
个技能槽位，以及每个槽位对应的手柄按键。

### 7.2 首版布局

-   两组技能槽：RT 组和 LT 组。
-   每组 8 个槽位。
-   使用 Xbox 风格按钮图标或简洁文字标签。
-   技能图标为视觉主体，按键标识作为辅助。
-   两组可并排、上下或左右排列，具体位置通过游戏内实测决定。
-   不把此前的文本布局示意视为最终美术稿，实际布局应在游戏 HUD 中迭代。

### 7.3 功能范围

  功能                   P0 要求                说明
  ---------------------- ---------------------- -------------------------
  16 个技能槽位          必须                   RT 8 + LT 8
  技能名称/缩写          必须                   可手工配置
  手柄按钮标签           必须                   与输入映射一致
  技能图标               先占位，后接真实数据   依赖图标 API
  冷却遮罩               可选                   API 验证通过后
  当前层高亮             可选                   需要可靠获知 RT/LT 状态
  HUD 显示/隐藏          必须                   不影响原生游戏输入
  HUD 缩放/位置/透明度   建议                   可分阶段实现
  门派技能自动识别       不要求                 后续研究

### 7.4 降级原则

如果 Lua 无法读取 RT/LT 状态：

-   同时显示两组技能。
-   不做当前技能层动态高亮。
-   玩家通过实际按键和静态 HUD 理解映射。

如果技能图标 API 不可用：

-   使用手工配置或占位图标。
-   不让动态技能数据依赖阻断 HUD 的开发。

如果冷却 API 不可用：

-   首版不显示冷却遮罩。
-   保留静态技能槽位和按键提示。

## 8. RingMenu：环形快捷菜单

### 8.1 目标

将低频但常用的功能集中到一个手柄友好的环形菜单，减少对键盘和鼠标的依赖。

### 8.2 候选八方向

  方向   菜单功能
  ------ -----------
  上     地图
  右上   背包
  右     任务
  右下   角色
  下     技能/武学
  左下   社交
  左     设置
  左上   返回/关闭

这只是第一版菜单信息架构草案，实际菜单项可按游戏 API
和玩家使用频率调整。

### 8.3 交互流程

1.  玩家主动按下菜单键打开 RingMenu。
2.  通过方向键或摇杆选择方向。
3.  当前选项高亮，并显示名称/图标。
4.  玩家按确认键执行。
5.  取消键关闭菜单或返回上一级。

### 8.4 实现限制

-   P0 不实现 RingMenu。
-   必须先验证 UI 输入焦点、方向导航和允许的窗口打开方式。
-   如果不能合法模拟 UI 点击，就改用快捷键提示或官方允许的窗口 API。
-   不通过菜单自动执行任务、整理背包或其他批量操作。

------------------------------------------------------------------------

## 9. Target HUD：目标信息显示

### 9.1 目标

为手柄操作提供更清晰的目标状态提示，降低玩家在原生小型信息区域之间切换视线的负担。

### 9.2 后续候选信息

仅在当前允许的只读 API 可提供时考虑：

-   目标名称。
-   目标类型。
-   其他官方允许公开的目标信息。
-   与原生界面重复的信息应避免重复展示。

### 9.3 不做的功能

-   自动锁定目标。
-   自动切换目标。
-   根据战斗状态自动选目标。
-   通过非公开数据推断目标信息。

目标 HUD 是信息展示层，不是战斗决策系统。

## 10. 配置与个性化

### 10.1 配置目标

让玩家能够按自己的门派、角色和设备调整操作方式。

### 10.2 配置维度

-   手柄逻辑布局：Xbox / PlayStation。
-   左摇杆死区。
-   右摇杆死区。
-   镜头水平/垂直灵敏度。
-   镜头反向。
-   RT/LT 两层技能槽位。
-   技能名称和图标。
-   HUD 显示/隐藏。
-   HUD 位置、缩放和透明度。
-   不同角色或门派的 Profile。

### 10.3 Profile 结构示意

``` text
Profile
├── device_layout
├── stick_settings
│   ├── left_deadzone
│   ├── right_deadzone
│   ├── camera_sensitivity_x
│   └── camera_sensitivity_y
├── hotbar
│   ├── rt_layer[8]
│   └── lt_layer[8]
└── hud
    ├── scale
    ├── opacity
    ├── position
    └── visible
```

### 10.4 配置原则

-   先实现一套默认 Profile。
-   再实现手动修改槽位。
-   最后再扩展多门派、多角色配置。
-   保存方式必须使用当前客户端允许的机制。
-   不保存账号密码、认证信息或其他敏感信息。

## 11. 关键使用场景

### 场景 A：日常移动与探索

1.  左摇杆控制角色移动。
2.  右摇杆调整视角。
3.  A 或指定按钮完成跳跃。
4.  玩家仍可随时使用键鼠完成复杂交互。

验收重点：移动与镜头同时控制自然，松杆后无持续输入。

### 场景 B：战斗技能操作

1.  玩家观察 HUD 上的 RT 技能组。
2.  按住 RT 并按下对应面键/方向键。
3.  输入映射触发游戏原生快捷键。
4.  玩家观察游戏原生战斗反馈与 HUD 信息。
5.  松开 RT，回到基础层或切换到 LT 技能组。

验收重点：修饰层覆盖正确、无双重输入、按键与 HUD 对应一致。

### 场景 C：技能组切换

1.  玩家按住 LT。
2.  使用相同的八个物理按键访问第二组技能。
3.  不需要改变手指位置或记忆另一套完全不同的按钮布局。

验收重点：LT 层输入稳定，松开后状态复位。

### 场景 D：非战斗菜单操作（后续）

1.  玩家按菜单键打开 RingMenu。
2.  用方向输入选择地图、背包、任务或角色面板。
3.  确认后打开对应界面。
4.  取消键返回游戏。

验收重点：焦点明确、菜单不会误触、玩家始终可退出。

### 场景 E：轻功移动（后续）

1.  左摇杆控制地面/空中方向。
2.  右摇杆控制视角。
3.  玩家手动触发跳跃和轻功相关技能。
4.  需要时使用 RT/LT 技能层。
5.  落地后自然恢复普通移动操作。

验收重点：空中方向与视角不互相阻塞，技能组合不造成移动卡顿。

## 13. 当前明确不做的内容

为了避免项目范围膨胀和规则风险，当前明确排除：

-   自动战斗、自动输出、自动连招、自动施法。
-   自动选择技能、自动切换目标或自动锁定。
-   自动寻路、自动轻功、自动完成任务。
-   自动采集、自动打本、自动整理物品等批量操作。
-   DLL 注入、进程 Hook、内存读写、封包操作。
-   绕过插件认证、白名单或客户端安全机制。
-   未经验证的 Lua 全局按键监听或原始手柄读取。
-   第一版就适配所有门派、所有客户端和所有手柄。

## 14. 核心体验验收标准

从玩家体验角度，MVP 应至少满足：

1.  玩家可以只用手柄完成基本移动、镜头和跳跃。
2.  玩家能通过 RT/LT 两层访问 16 个手动技能位。
3.  HUD 上的按键提示与实际映射完全一致。
4.  修饰层不会触发基础层的意外动作。
5.  输入焦点切换、聊天框、桌面切换和设备断连不会造成卡键或误施法。
6.  玩家可以随时使用键鼠，不会被插件锁死。
7.  插件可以关闭或隐藏，且不影响原生游戏。
8.  所有使用的 API 和映射方式都经过当前规则与客户端验证。

## 16. 当前产品决策摘要

截至 2026-11-02，JX3 ConsolePort 的核心方向可以概括为：

1.  **平台**：PC 旗舰版优先。
2.  **产品形态**：手柄输入适配 + Lua 交互 HUD，而非单纯映射器。
3.  **输入方案**：优先调查官方原生输入；P0 候选为规则允许的 Steam Input
    键鼠映射。
4.  **战斗布局**：RT/LT 双修饰层，每层 8 个槽位，共 16 个手动技能位。
5.  **核心 UI**：CrossHotbar 十字技能栏。
6.  **移动与视角**：左摇杆 WASD、右摇杆相对鼠标作为初始候选。
7.  **剑三特色**：轻功作为后续独立操作模式重点研究。
8.  **后续界面**：RingMenu、Target HUD、门派 Profile。
9.  **实现原则**：API
    白名单优先、玩家主动输入、无自动战斗、无客户端注入。
10. **开发顺序**：先确认规则和加载，再验证输入，最后开发 HUD
    与扩展功能。

**项目最重要的产品判断：我们要做的是"让剑三真正适合用手柄玩"，而不是"让手柄能够按出键盘按键"。**

这句话是后续功能取舍、UI 设计和开发优先级的总原则。
