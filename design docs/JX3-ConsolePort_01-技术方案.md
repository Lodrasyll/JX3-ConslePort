# JX3 ConsolePort（PC 旗舰版）技术方案

> 文档编号：JX3CP-TECH-001｜版本：v0.1｜日期：2026-11-02\
> 目标平台：Windows PC《剑网3》旗舰版\
> 状态：技术预研，尚未通过当前客户端实测

## 0. 文档目的与结论边界

本文整理目前讨论形成的技术方案，作为后续原型开发的共同基线。

文中信息分为四类：

-   **已有项目线索**：公开插件源码或历史资料中出现过相关实现。
-   **待当前客户端验证**：历史代码中存在，不代表当前旗舰版仍可用。
-   **设计目标**：希望实现的产品体验，不代表技术已验证。
-   **禁止路线**：不采用客户端注入、进程
    Hook、内存读写、绕过认证或自动化战斗。

重要：茗伊等插件源码中的函数可能是插件框架内部封装，并不等于剑网3客户端向第三方插件公开的全局
API。每个函数都必须核对来源、当前客户端版本、白名单状态、调用签名和真实行为。

## 1. 项目目标

### 1.1 一句话目标

为《剑网3》PC 旗舰版开发 ConsolePort 风格的手柄交互插件，使玩家能使用
Xbox、PlayStation
或兼容手柄完成常用移动、视角、技能快捷键和界面操作，并通过 Lua
插件提供手柄友好的 HUD、技能栏和快捷菜单。

### 1.2 参考方向

-   **WoW ConsolePort**：手柄操作理念、组合键、虚拟鼠标、HUD。
-   **FFXIV Cross Hotbar**：技能分层与组合键布局。
-   **Steam Input**：P0 阶段的外部输入映射候选工具。

借鉴的是交互设计和模块化方式，不是把 WoW 插件代码直接移植到剑三。

### 1.3 P0 / MVP 目标

1.  手柄能完成基本移动、视角和跳跃。
2.  RT、LT 两个修饰层映射最多 16 个手动技能位。
3.  Lua 插件显示与实际映射一致的十字技能栏 HUD。
4.  建立最小配置入口和调试信息。
5.  验证输入映射、游戏 API 和 UI 显示之间的边界。

### 1.4 非目标

P0
不实现自动输出循环、自动连招、自动施法、自动选招、自动锁定、自动寻路、自动采集、自动打本等功能；不开发驱动级手柄输入、不读写游戏进程内存、不修改封包、不注入
DLL、不绕过签名或插件白名单，也不假定 Lua 能直接读取 XInput /
DirectInput 原始数据。

### 2.1 两条输入路线

**路线 A：游戏原生手柄输入**

若 PC
旗舰版存在官方开放且允许插件使用的手柄接口，优先采用。优点是摇杆、扳机和按键状态更自然；目前尚未确认该接口存在。

**路线 B：Steam Input 键鼠映射 + Lua HUD**

P0 优先验证：

-   Steam Input 识别手柄。
-   Steam Input 将输入转换为键盘或鼠标动作。
-   剑三继续使用原生键位和技能栏。
-   Lua 插件显示 HUD、图标、冷却和操作提示。
-   Lua 是否能获知 RT/LT 状态单独验证；不能获知时，HUD
    先静态展示两组技能。

这不是"Lua 读取手柄"，而是"外部工具完成输入映射，Lua
插件提供视觉层"。具体映射必须先确认符合游戏规则。

## 3. 总体架构

``` text
Xbox / PlayStation / 兼容手柄
              |
              v
       Steam Input（P0 候选）
       手柄 -> 键盘/鼠标
              |
              v
      剑网3 PC 旗舰版原生输入
      移动 / 视角 / 技能键位
              |
              +-------------------+
              |                   |
              v                   v
        游戏原生技能栏         Lua 插件 UI
                                  |
                                  v
                       JX3 ConsolePort
                       - CrossHotbar
                       - TargetHUD
                       - RingMenu（后续）
                       - Settings / Profile
                       - GameAPI Adapter
```

### 3.1 分层职责

  层                      职责                           不负责
  ----------------------- ------------------------------ -----------------------
  Hardware                手柄物理按键与摇杆             游戏技能逻辑
  Input Mapping           手柄映射到键鼠                 读取游戏内部状态
  Game Native Input       游戏原生键位、技能栏、镜头     插件 HUD
  Lua Plugin              HUD、配置、状态显示、UI 导航   未授权进程数据
  Compatibility Adapter   隔离客户端 API 差异            假定历史 API 当前有效

### 3.2 模块职责

-   **InputAdapter**：P0
    管理映射配置和槽位元数据；不假装接收原始手柄事件。未来若有官方手柄
    API，再增加原生适配器。
-   **GameAPI**：所有经过验证的游戏 API
    的唯一封装入口；记录来源、版本、许可、参数、返回值和失败行为。
-   **CrossHotbar**：显示技能槽位、图标、按键标签、冷却信息。未验证技能
    API 前使用占位图/手工配置。
-   **RingMenu**：P0
    后续开发，提供地图、背包、任务、角色、社交等快捷入口。
-   **Profile /
    Settings**：保存布局、缩放、透明度、槽位说明等设置；只使用当前允许的配置保存机制。

## 5. API 验证清单

### 5.1 四级验证标准

  级别          内容                               证据
  ------------- ---------------------------------- ----------------------------
  A：来源确认   函数出现在哪个项目/文件            源码路径、版本、许可证
  B：当前存在   当前客户端插件环境中可访问         当前版本测试记录
  C：许可确认   当前官方规则允许调用               官方文档、白名单或明确许可

只有 A/B/C/D
全部通过，才可进入正式业务代码。仅在其他插件源码看到函数名，不代表可以直接调用。

## 6. 插件加载测试

### 6.1 前置条件

1.  记录客户端版本、安装路径和启动方式。
2.  确认当前官方插件开发、测试和认证政策。
3.  确认自制插件是否允许在当前客户端加载。
4.  备份现有插件目录。
5.  使用独立 `JX3CP_P0` 目录，不覆盖其他插件。
6.  不修改客户端文件，不关闭安全校验，不绕过签名或认证。

### 6.2 历史入口格式参考

``` ini
[JX3CP_P0]
name=JX3CP Prototype P0
desc=Controller HUD prototype
version=0.1
default=0
lua_0=Main.lua
```

这是历史格式参考。节名、字段、编码、入口文件字段和插件启用方式都必须在当前官方规则下验证。

### 6.3 加载验收

-   插件管理器能否识别插件。
-   是否存在官方允许的测试/认证方式。
-   入口是否执行。
-   Lua 语法错误能否定位。
-   插件关闭/卸载时是否清理事件与 UI。
-   插件未加载时游戏是否正常。
-   与常用插件共存时是否有 UI 冲突。
-   不覆盖其他插件文件。

## 7. P0 手柄输入方案

### 7.1 基础布局

  手柄输入           P0 候选行为               备注
  ------------------ ------------------------- ------------------------------
  左摇杆             WASD                      初期数字移动；测试斜向与死区
  右摇杆             相对鼠标移动              测试是否需要按住鼠标键
  A                  跳跃 / RT 技能 1          修饰层必须覆盖基础层
  X                  基础交互 / RT 技能 2      基础功能待定
  Y                  菜单 / RT 技能 3          避免与原生命令冲突
  B                  取消/返回 / RT 技能 4     需确认焦点行为
  十字键             常用操作 / RT 技能 5--8   基础层用途后定
  RT + 面键/方向键   技能 1--8                 玩家手动触发
  LT + 面键/方向键   技能 9--16                玩家手动触发
  Menu / View        后续菜单入口              P0 不强制实现

### 7.2 技能槽位映射候选

  槽位      RT 层输出   LT 层输出
  --------- ----------- -----------
  A         `1`         `Ctrl+1`
  X         `2`         `Ctrl+2`
  Y         `3`         `Ctrl+3`
  B         `4`         `Ctrl+4`
  D-pad ↑   `5`         `Ctrl+5`
  D-pad ←   `6`         `Ctrl+6`
  D-pad →   `7`         `Ctrl+7`
  D-pad ↓   `8`         `Ctrl+8`

仅为示例。需先排除游戏原生键位冲突，并确认游戏接受组合键、映射方式符合规则。

### 7.3 修饰层必须解决的问题

-   RT 按住时，A 不应同时触发基础层跳跃和 RT 技能。
-   LT 按住时，基础层按键不应意外触发。
-   P0 暂不定义 LT+RT 第三层。
-   松开扳机时不得残留 Ctrl/Shift 状态。
-   游戏失焦、聊天框聚焦、输入法切换时不得意外施放技能。
-   手柄断开后不得持续输出按键。

### 7.4 摇杆验收

**左摇杆**：初始映射 WASD；测试死区、斜向、对角线速度、短点移动。P0
不承诺模拟量行走。

**右摇杆**：初始映射相对鼠标；测试水平/垂直灵敏度、反向、加速度、死区、镜头边界，以及是否需要持续按住右键。不假定
Lua 能控制镜头。

### 7.5 输入测试用例

1.  静止时按 A：只触发基础层功能。
2.  按住 RT 再按 A：只触发 RT 层技能。
3.  按住 LT 再按 A：只触发 LT 层技能。
4.  快速连续按键：每次物理按键只产生一次预期输入。
5.  长按扳机并连续按不同按键：无串键。
6.  松开扳机：修饰层恢复正常。
7.  聊天框聚焦：不意外施放技能。
8.  切换桌面：不持续产生游戏输入。
9.  手柄断开/重连：无卡键或持续移动。
10. 左右摇杆同时操作：移动与镜头互不阻塞。

## 8. HUD 与交互设计

### 8.1 CrossHotbar P0

显示 16 个技能槽位，分为 RT 与 LT 两组。每槽可包含：

-   技能图标（API 未验证前用占位图或手工配置）。
-   技能名称/缩写。
-   按键标签（A/X/Y/B/方向键）。
-   技能层标签（RT/LT）。
-   冷却遮罩（仅在冷却 API 验证通过后）。
-   当前层高亮（仅在能可靠获知当前层时）。

P0
不要求自动识别所有门派技能，可先由玩家手动填写技能名称、图标和键位说明。

### 8.2 TargetHUD

P0
只预留位置。后续仅接入当前允许的只读目标信息；不实现自动锁定、自动切换或自动选择目标。

### 8.3 RingMenu

P0 后续开发，建议 8
个固定方向：地图、背包、任务、角色、技能/武学、社交、设置、返回/关闭。每项操作由玩家主动选择；若无法合法模拟
UI 点击，则改为快捷键提示或允许的窗口 API。

### 8.4 UI 原则

-   不遮挡原生战斗信息。
-   支持缩放、移动、透明度和隐藏。
-   键鼠玩家可关闭 HUD。
-   静态信息不逐帧重绘。
-   动态冷却采用合理刷新频率。
-   不在每帧执行大量 API 查询。

## 10. 安全、规则与发布

采用"官方允许的插件接口 + 玩家手动输入"的路线。

不采用 DLL 注入、进程
Hook、内存读写、封包修改、驱动级伪装、绕过安全机制、自动连发、自动连招、自动战斗或自动目标选择。

发布前确认：

1.  当前旗舰版插件政策。
2.  自制插件开发/测试/认证流程。
3.  API 白名单和审核要求。
4.  外部手柄映射是否符合游戏规则。
5.  是否允许公开分发。
6.  第三方源码许可证与再分发限制。

## 11. 风险清单

  风险                         等级   应对
  ---------------------------- ------ --------------------------------
  自制插件无法加载             P0     先确认官方政策与测试渠道
  历史 API 当前不可用          P0     建立版本化 API 验证表
  内部封装被误认成客户端 API   P0     标注来源层级，不直接调用
  Lua 无法获知 RT/LT           P1     HUD 静态显示两组技能
  Steam Input 与游戏键位冲突   P1     独立键位方案、逐项测试
  修饰层双重输入               P1     测试覆盖优先级、松键与焦点变化
  右摇杆镜头不稳定             P1     单独测试鼠标映射和按键条件
  技能冷却不可读               P1     P0 先不显示真实冷却
  UI 兼容性差                  P2     先固定分辨率，再扩展适配
  第三方许可证不兼容           P2     只参考设计或按许可证使用

## 13. 当前技术结论

最现实的第一条路线是：

**Steam
Input（规则允许时）负责手柄到键鼠的映射；剑三原生输入负责实际操作；Lua
插件负责 HUD、技能栏和后续菜单。**

当前最大不确定性不是 UI 怎么画，而是：

1.  PC 旗舰版当前是否允许自制插件加载与测试。
2.  哪些 Lua API 当前被允许。
3.  游戏能否稳定接收外部手柄映射。
4.  Lua 能否读取足够的技能信息，以及能否获知 RT/LT 状态。

因此第一道里程碑必须是"规则确认 + 插件加载验证 +
输入映射验证"，通过后再投入完整 HUD 开发。
